# NV: IRC, Party и синхронизация визуала

Собственная реализация социальных каналов для текущего клиента. Проверенная конфигурация: FastAPI 0.141.1, Uvicorn 0.52.4, websockets 17.0.1, один процесс. Голосовой движок отсутствует; `/health` сообщает `voice: false`, голосовые настройки клиент скрывает.

## Работающая установка

- Публичный адрес: `https://virion.185-56-162-195.sslip.io/nv`.
- Сервис: `nv-backend.service`, пользователь `nv-social`.
- Код и собственное окружение: `/opt/nv-backend/server.py`, `/opt/nv-backend/venv`.
- Данные: `/var/lib/nv-backend/nv-social.sqlite3`, SQLite WAL, каталог 0700.
- Uvicorn слушает `127.0.0.1:8080`. Nginx завершает TLS и проксирует только `/nv/`; для сокетов передаёт Upgrade.
- Конфигурация Nginx: `/etc/nginx/snippets/nv-social.conf`, include в существующем HTTPS virtual host. Действующие пути Virion сохранены.
- Исходная резервная копия: `/opt/nv-backend/backups/20260930-social-v2`. В ней есть старый сервис, код, Nginx и приватный снимок прежнего IRC. Последующий update создаёт отдельный снимок кода и согласованный SQLite backup.

Текущий адрес использует существующий сертификат и DNS sslip.io. Для постоянного продукта нужен принадлежащий владельцу домен NV с отдельным virtual host; его адрес в этой работе не был предоставлен.

## Протокол и границы доверия

`POST /api/session` принимает UUID установки, случайный секрет из 32 байт и ник длиной 3–16 символов. Секрет хранится на сервере в виде SHA-256; повторная авторизация требует тот же секрет. Резервирование ника нечувствительно к регистру. Bearer живёт 24 часа и передаётся через заголовок Authorization, в том числе при WebSocket handshake. После перезапуска токены забываются; клиент повторяет авторизацию сохранённой установкой. Не помещать секрет или токен в URL, логи и отчёты.

**Это идентификация установки, а не доказательство владения Minecraft-аккаунтом или покупки.** Первый зарегистрировавший ник может его занять. Ник, присланный в сообщении, не даёт права отправлять от другого профиля. Доверенные роли, UID и права на коммерческие косметические предметы требуют отдельной интеграции с системой аккаунтов. В текущей синхронизации роль принудительно Guest, аватар пустой.

| Канал | Адрес | Поведение |
|---|---|---|
| IRC | GET `/api/messages`, POST `/api/send` | Публичные и личные сообщения, отправитель определяется сессией. PM видит только отправитель и получатель. Параметр `me` не меняет доступ. |
| Presence | GET `/api/presence` | Реальные активные профили; серверный TTL 15 секунд, клиент не считает кеш актуальным дольше 10 секунд. |
| Party | WSS `/party` | Создание, приглашение, принятие/отказ, выход, kick, disband, чат, markers/spit, повторное соединение и передача лидерства. |
| GUI | WSS `/sync/gui` | Ограниченные snapshot/delta состояния в одном идентификаторе мира. Включение публичной передачи GUI требует настройки клиента. |
| Питомцы | WSS `/sync/pets` | Дух, дракон, мотылёк и ограниченная совместимость со старыми вариантами. |
| Эмоции | WSS `/sync/emotions` | Передача состояния анимации; наличие работающего локального animation bridge проверяется отдельно. |

Идентификатор мира выбирает клиент. Это разделение комнат, оно не доказывает членство на игровом сервере. Для приватных серверных миров нужен сервером подписанный пропуск. Передаваемые GUI-настройки видны участникам комнаты: не добавлять в snapshot секреты и account-токены.

## Ограничения ресурсов

- HTTP/WS JSON: 64 KiB на входе, конечные числа, объект верхнего уровня, глубина до 8, до 128 полей/элементов.
- Координаты до ±30 млн; приглашение привязано к получателю, срок 60 секунд; группа до 10 участников.
- Сокеты: максимум 256 peers суммарно, очередь отправки 64, timeout 5 секунд для медленного получателя. Uvicorn ограничивает отдельное сообщение и очередь WS.
- HTTP rate limit по IP; WS rate limit по сессии; отдельный лимит отправки IRC. За общим NAT лимит IP разделяется пользователями.
- Для исчезнувших GUI/pet/emotion состояний есть TTL: состояние без обновления 10 секунд удаляется при очередном обслуживании каждые 5 секунд. При нормальном закрытии удаление передаётся сразу.
- Данные сообщений, установки и состав Party сохраняются. Presence, приглашения, токены и временные визуальные состояния после рестарта очищаются.

**Запускать один worker.** Онлайн-состояние и маршрутизация сокетов живут в памяти процесса. Несколько workers или несколько серверов требуют общего брокера и shared storage для маршрутизации. SQLite commits выполняются синхронно; нагрузочная проверка сотен пользователей не проводилась. Не объявлять найденные лимиты доказанной пропускной способностью.

## Проверки

`verify_protocol.py` проверяет живые HTTP/WSS каналы: авторизацию, PM-изоляцию, подмену отправителя, размер сообщений, приглашения/лидера, reconnect, world separation и удаление peers. Секреты создаются в памяти и не печатаются. Тест публикует несколько явно обозначенных тестовых сообщений и создаёт временные профили; использовать на staging либо по согласованному обслуживанию.

`verify_persistence.py` самостоятельно запускает изолированный сервис на свободном localhost-порту с временной БД, перезапускает его и проверяет сохранение установки, IRC и Party плюс инвалидирование старого токена. Он не трогает рабочий VDS.

В Java suite `SocialNetworkTest` проверены реальные IrcClient, PartyClient, ClientPresence и три sync-клиента из remapped JAR через публичный TLS endpoint. Второй peer — протокольный клиент; двух одновременно играющих пользователей на настоящем Minecraft-сервере этот сценарий не заменяет.

Результаты: `docs/verification/backend-vds-public-final.json`, `backend-restart.json`, `backend-vds-final.txt`; лог игрового сетевого сценария фиксируется в итоговом отчёте.

## Обновление и откат

Скрипты в `deploy` документируют фактически использованное развёртывание. Сначала положить новую версию в `/opt/nv-backend/staged/server.py`, проверить Python-компиляцию и локальный протокол. `update.sh` сохраняет исходный файл и SQLite через backup API, устанавливает код через `.part` и rename, перезапускает только NV и проверяет localhost health. При неуспешном health возвращает прежний код, сохраняя текущую БД. Хеш опубликованного кода сверять с локальным SHA-256. После этого повторить публичный HTTPS/WSS smoke test.

`rollback.sh` возвращает первоначальные код, unit и Nginx из первой резервной копии. Текущую БД сохраняет. Это возвращение старого протокола с его исходными ограничениями, а не восстановление новых социальных данных в старую реализацию. Для обычного отката новой версии предпочтительнее вернуть последний проверенный `server.py` из update-backup.

Для диагностики: статус `nv-backend.service`, журнал этой службы, localhost health и публичный `/nv/health`. Не выводить SQLite identities/PM в публичные логи. Перед изменением схемы нужна отдельная миграция и проверка восстановления; текущий update не предназначен для необратимой смены схемы.
